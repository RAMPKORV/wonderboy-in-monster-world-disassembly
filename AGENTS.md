# AGENTS.md â Sega Genesis ROM Disassembly Base

This folder is a **reusable base** for disassembling ANY Sega Genesis / Mega
Drive ROM into bit-perfect 68000 assembly source. You are the agent working
here.

To use it for a new game: copy this folder, put the ROM somewhere, run
`node tools/setup.js <rom.bin>`, and start working. Read the rest of this
file, then `docs/segagenesis.md`, `docs/pipeline.md`, `docs/asm68k.md`, and
`docs/workflow.md`.

## Environment

- **Working directory safety**: all operations stay inside this project
  folder.
- **Assembler**: `asm68k.exe` (SN System 68k v2.53), run via wine.
- **Decoders**: Ghidra headless (`/opt/ghidra/support/analyzeHeadless`,
  scripts in `tools/ghidra/`) or `tools/m68kdis.js` as a fallback.
- **Scripting**: Node.js only (no Python).
- **Testing**: there are no unit tests. **Bit-perfect verification is the
  only test.** `./verify.sh` must always print
  `BUILD VERIFIED - ROM IS BIT-PERFECT`.

## The Goal

Reconstruct the original 68000 source that assembled the ROM, such that
`./build.sh` + `./verify.sh` reproduce the ROM byte-for-byte. Secondary
goal (if the user wants it): document the engine for re-implementation.

## The One Golden Rule

**The ROM bytes are the only truth.** Ghidra decodes, asm68k assembles â
when they disagree with the ROM bytes, the ROM wins. Emit the exact ROM
bytes (usually `dc.w`) and move on.

## Command Reference

```bash
./build.sh                        # assemble wonderboy.asm -> out.bin
./verify.sh                       # hash-check out.bin vs the ROM
node tools/setup.js "<rom.bin>"   # one-time project init from a ROM
node tools/regen_rest.js game.rom # rebuild data_rest.asm from regions.json
node tools/extract_assets.js      # ROM -> assets/tiles.png + palettes.json (lossless)
node tools/regen_assets.js        # assets -> src/data/tile_blocks_*.asm + palette_table.asm
node tools/autofix.js game.rom src/<mod>.asm <startHex> <endHex>  # converge
node tools/regiondiff.js game.rom <startHex> <endHex>              # diff
node tools/findfirstdiff.js game.rom out.bin                       # first diff
node tools/dumpdata.js game.rom <startHex> <endHex>                # bytes -> dc.b
```

**Asset pipeline:** `assets/` (tiles.png, palettes.json) is wired into
`build.sh` via `regen_assets.js`. Unmodified assets rebuild bit-perfect;
edited assets (same size/format) flow through with no pointer changes.
See `docs/pipeline.md`.

## Build Structure

- `wonderboy.asm` â top-level entry: includes `header.asm` + `data_rest.asm`.
- `header.asm` â includes `macros.asm`, `src/hw_constants.asm`,
  `ram_addresses.asm`, `sound_constants.asm`, `src/game_constants.asm`,
  then the auto-generated `src/header_vectors.asm`.
- `ram_addresses.asm` â named RAM symbols (`RAM_<type>_<hex>`); hand-named
  for traced state, auto-named `RAM_word_/long_/byte_<hex>` for the rest.
- `src/header_vectors.asm` â AUTO-GENERATED raw bytes $000-$1FF
  (exception vectors + ROM header). Do not hand-edit.
- `data_rest.asm` â AUTO-GENERATED by `tools/regen_rest.js`: it `include`s
  each region module in ascending ROM-address order and emits all remaining
  bytes as raw `dc.b`. Do not hand-edit.
- `tools/regions.json` â the manifest of converted regions:
  `[ { "file": "src/engine/core.asm", "start": "200", "end": "400", "label": "..." } ]`.
  **start/end are hex ROM ranges, end exclusive, sorted ascending, no
  overlaps.**
- `src/*.asm` â the disassembled modules (see code style below).
- `game.config.json` â decoded ROM header (written by setup.js).
- `game.rom.sha256` â expected hash used by verify.sh.

## Starting a NEW game (fresh copy, no work done)

Do these in order:

1. **Interrogate the user**: game + revision, goals, any material they have.
   Ask before assuming.
2. **Web research** the game: serial, existing disassemblies (Sonic Retro,
   romhacking.net, GitHub), engine articles, manual, level formats.
   Record findings in `docs/game-notes.md` (create it).
3. **Run setup**:
   ```bash
   node tools/setup.js "/path/to/Game (USA).bin"
   ```
   Confirm the baseline build is bit-perfect.
4. **Map the boot flow**: reset vector â entry point â VDP init â Z80
   boot â state dispatch. Identify the state machine. Write the region
   plan in `docs/game-notes.md`.
5. **Convert the first region** (core/boot), register it, converge,
   verify, commit.
6. **Work through the plan**, committing after each verified region and
   updating `docs/progress.md`.

## "Continue working" / "Work according to plan"

- Read `docs/progress.md` + `tools/regions.json` to find where things are.
- Convert the next region: decode â author â register â regen â autofix â
  verify â commit.
- Update `docs/progress.md` after each verified region.
- If all planned regions are done, finish with engine documentation

## Code Style

- **Labels** at column 0; instructions indented one tab.
- **Mnemonics UPPERCASE**, size suffixes lowercase: `MOVE.w`, `TST.l`.
- One instruction per source line with a `; $ADDR` trailing comment.
- Branch size: `.b` for short (Â±127), `.w` otherwise. JSR/BSR for calls;
  JMP/BRA for jumps.
- **Keep hex** for addresses, hardware values, bitmasks, and data tables.
  `dc.w`/`dc.b`/`dc.l` data must stay hex â `$0000` is not `0`.
- Safe to use decimal for instruction immediates: `MOVE.w #0, D0`.
- Labels: `loc_XXXXXXXX` while unnamed; rename to PascalCase once
  understood, keeping the address comment: `; loc_0000633C` /
  `MapRLEDecompressor:`. Rename globally (labels may be cross-referenced
  between modules) and rebuild.
- **Named RAM symbols**: use `ram_addresses.asm` symbols (`RAM_PlayerState`)
  instead of raw hex in operands; add symbols there as addresses are
  understood.
- **Routine doc blocks**: once a routine is named, add a `; ------` block
  above it describing purpose and inputs/outputs (zoom-style):
  ```
  ; ----------------------------------------------------------------------
  ; ResolveScene: resolves a scene index via the scene table; stores the
  ; scene data pointer to RAM_SceneDataPtr and returns the type entry in A1.
  ; ----------------------------------------------------------------------
  ```
- Module file names describe the subject (`movement.asm`, `menu_system.asm`,
  `scene_loader.asm`), not an ordinal. Files live in per-subject
  subdirectories under `src/`: `engine/`, `gameplay/`, `scene/`, `data/`,
  `z80/`. Data banks are consolidated by region (e.g. `src/data/main_data.asm`
  covers the whole $A000-$20000 bank), not split into arbitrary chunks.
- Section banners:
  ```
  ; ======================================================================
  ; src/engine/core.asm
  ; Boot + init, state dispatch.
  ; ======================================================================
  ```
- Shared constants (ROM data pointers, state values) go in
  `src/game_constants.asm`; RAM symbols in `ram_addresses.asm` (both
  included first via `header.asm`). Routine labels forward-reference freely
  across modules.

## The Autofix Process (do not skip)

1. Author `src/<name>.asm` for a contiguous region.
2. Append the module to `tools/regions.json`.
3. `node tools/regen_rest.js game.rom`
4. `node tools/autofix.js game.rom src/<name>.asm <start> <end>`
5. `./verify.sh`

`autofix.js` replaces any line whose asm68k encoding differs from the ROM
with the exact ROM bytes (`dc.w`), looping to convergence. If it reports
`listing entries != source instr`, the module size is wrong â fix the
instruction, do not let autofix guess.

**Known asm68k/Ghidra gotchas** (full detail in `docs/asm68k.md`):
- Forward `.b` branches to later labels â displacement $00. Use `*+N`
  where `N = target â addr` (displacement = N â 2). Backward `.b`, all
  `.w`/`.l` forward branches are fine.
- Branch displacement is relative to `addr+2` for every branch.
- Ghidra normalizes `MOVE.W #byte,Dn` to `moveq` (2 bytes short). Restore
  the true width.
- Ghidra misprints absolute addresses and can skip instructions. Trust ROM
  bytes; keep `; $ADDR` hints monotonic.
- `MOVE (An)` short form vs `$00(An)` d16 form â match the ROM.
- Shift-count `#1` encoding differs (`$E148` vs `$E348`).
- Indexed-PC forms must be emitted as `dc.w` (e.g. `$4EBB` jmp).
- `dc.w` multi-values: NO space before commas (asm68k drops values).
- Wrong loop labels are the #1 autofixâ`dc.w` cause. Target = addr+2+disp.

## Verification

There are **no unit tests**. After ANY code change:
1. `wine asm68k.exe /k /p /o ae- wonderboy.asm,out.bin,,game.lst` (zero errors)
2. `./verify.sh` â `BUILD VERIFIED - ROM IS BIT-PERFECT`

A non-bit-perfect build is never acceptable. Do not proceed until clean.
Commit each verified module (small, frequent commits).
